# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Архитектурное решение: Периодические задачи (Recurring Tasks)

Для реализации функционала периодических задач был выбран подход "Eager Generation" (Предварительная генерация).

Как это работает:
Когда пользователь создает задачу с настройками повторения (например, recurrence_type: "daily"), создается основная задача-шаблон (Parent Task).

На уровне Usecase запускается генератор, который вычисляет даты для следующих 30 дней в соответствии с правилом повторения.

Для каждой вычисленной даты создается отдельная дочерняя задача (Child Task), связанная с шаблоном через parent_id и имеющая конкретную дату в поле scheduled_at.

Обоснование решения (Почему так?):
Быстрое чтение (Fast Reads): При запросе списка задач на сегодня/завтра (для отображения в календаре врача), базе данных не нужно "на лету" вычислять сложные правила периодичности. Задачи уже существуют в БД.

Независимость экземпляров: Врачи могут отменить или изменить описание задачи на один конкретный день, не ломая при этом всю цепочку повторений (так как каждая задача — это отдельная запись в БД).

Ограничения и компромиссы (Trade-offs), учтенные в решении:
Bulk Inserts: На данный момент генерация 30 задач вызывает 30 отдельных INSERT запросов в БД. В реальном production-коде под высокой нагрузкой этот механизм необходимо оптимизировать через Bulk Insert (множественная вставка одним запросом).

Ограничение горизонта планирования: Задачи генерируются только на 30 дней вперед. Для бесконечных задач в production потребуется фоновый процесс (Cron job / Worker), который раз в сутки будет догенерировать новые задачи для тех цепочек, у которых заканчивается "горизонт".

Timezones (Часовые пояса): В системе предполагается, что все даты хранятся в UTC. При работе врачей из разных регионов Frontend должен конвертировать локальное время врача в UTC перед отправкой на сервер.
